The specification

What Delta does, exactly: the loop, the limits, the tool set, the session format, the CI surface and the extension contract. The same text ships inside the binary as delta docs.

1. The turn

A turn is prompt → provider (streaming) → tool calls → results → next step until the model answers without asking for a tool. Delta owns the loop and the tools; the model only asks. Ceilings, all overridable by env:

DELTA_MAX_STEPS      200      steps in one turn
tool output          200 KB   per tool result (process is killed at the cap)
context              8 MB     per request; above it, emergency prune (4 outputs x 20 KB)
empty provider turn  6 nudges after an HTTP 200 with nothing inside, then a real error

2. Tools

read write edit undo bash ls find grep graph plus the unified families fs shell git web memory code assert agent extend skills mcp extensions, each taking an op. Every write keeps an undo snapshot. bash runs with a timeout, converts Windows OEM output to UTF-8, and is killed when ESC/Ctrl+C asks to stop (exit code 130).

3. Sessions

One JSONL per session, per folder:

~/.deltaCore/sessions/--<folder-slug>--/<date>_<id>.jsonl
{"type":"session","version":3,"id":"...","cwd":"..."}
{"type":"message","message":{"role":"user|assistant|tool", ...}}

delta                 new chat (always)
delta continue        reopen this folder's last chat, thinking included
delta export          markdown transcript of the last session
delta export --json   NDJSON of the same messages

4. CI surface

delta -p "review src/" --json     # NDJSON, one event per line
{"type":"text","text":"..."}
{"type":"thinking","text":"..."}
{"type":"tool_call","name":"bash","args":"{...}"}
{"type":"tool_result","name":"bash","ok":true,"seconds":1.1,"bytes":10}
{"type":"turn_end","in":1234,"out":456}
{"type":"error","message":"..."}

# exit codes: 0 ok · 1 agent error · 124 command timeout

5. Extensions

One manifest can change several parts of the harness at once. Old one-capability-per-entry files keep working.

[
  {
    "name": "guardrails",
    "enabled": true,
    "prompt":   "rules appended to the system prompt",
    "tools":    [{"name": "x", "arg": "cmd", "desc": "...", "schema": "{...}"}],
    "commands": [{"name": "deploy", "arg": "optional prompt", "exec": "cmd"}],
    "hooks":    [{"event": "tool_call", "arg": "cmd"}],
    "ui":       {"status": "cmd"}     // third footer line
  }
]

6. Hook events

A hook is code, not a prompt: the harness runs it, so a blocked call never happens. Payload arrives as a JSON file path in argv[1]; the reply is JSON on stdout; 5 s timeout, 8 KB cap, fail-open.

tool_call      {"block":true,"reason":"..."} | {"args":"{...}"}
tool_result    {"output":"..."} | {"append":"..."}
user_message   {"block":true,"reason":"..."}      before any request leaves
turn_start     ignored reply                       before each provider call
turn_end       ignored reply
session_start  once per process

7. Data

~/.deltaCore/
  config.json   auth.json   models.v2.json   memory.json
  sessions/  skills/  mcps/  extensions/  graphs/  hooks/  themes/  undo/
  system/prompt.md     re-read every turn (your team rules live here)

Every file is written to a temporary and swapped in one step, so two windows never read half a config.

8. Known limits

macOS ships source only (no prebuilt binary). Linux desktop integration is untested. Secrets live in auth.json in plain text — the OS keyring is not wired yet. There is no system sandbox: hooks and extensions run with the same permissions as Delta. The UI is not extensible: no in-process plugin, so no widgets, keys or overlays from an extension.
